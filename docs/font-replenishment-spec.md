# 字体补录规范

版本：v1（2026-11-19，Asia/Shanghai）。后续若修改强制清单或完成定义，应在本文顶部递增版本并在 Changelog 留下文档变更记录。

本规范定义仓库内“把字形写入字体”之后必须留下什么记录、同步哪些文件、如何验收和提交。它适用于标准 Unicode 码位、项目 PUA 字位、既有码位的字形修订、字体文件替换，以及会改变字体加载结果的缓存戳更新。

本规范是执行要求；具体命令仍以[字体补录流程](research/2026-11-13-kangxi-字体补录流程.md)和目标工具的 `--help` 为准。身份判定、Unicode 归属和“是否真的缺字”先按[未编码字头字体核验流程](research/2026-11-13-kangxi-未编码字头字体核验流程.md)完成。

## 1. 不可省略的原则

1. **先判定，再写字体。** 已经在目标字体中存在的字形，不得仅因站方索引、OCR 或当前页面显示异常而重复补录。
2. **标准码位与 PUA 分开。** 已确认的 Unicode 码位写入目标字体的正式 cmap；未确认独立码位的项目异体才使用 PUA。标准码位不得为了方便写进 PUA 注册表。
3. **每次字体字节变化都必须可追溯。** 至少同时具备补录详报、Changelog 事件、操作登记簿行、机器证据、补前回滚点和 Git 提交。
4. **历史快照不追改。** 旧报告中的统计、哈希和结论属于当时快照；后续变化在报告开头补“后续共享字体状态”或新增事件，不覆盖原始证据。
5. **验证失败不得写入。** 干跑、保护检查、字形／度量验证或渲染验收任一失败，都只能保留诊断产物，不能把临时字体替换为生产字体。

## 2. 每次正式补录必须产出的文件

### 2.1 补录详报：一字一报告或一组同批报告

路径使用 `docs/research/YYYY-MM-DD-<码位或字形>补录报告.md`。报告至少包含：

- **身份与出处**：页码、字头序号、原文语境、用户提供的形体与实际定位差异；Unicode 码位、IDS、异体或未确认状态。
- **字体核验**：目标字体、候选后备字体、现有 cmap／隐藏未映射字形检查结果，以及“为什么需要补录”的证据边界。
- **范围决定**：写入哪些字体，哪些字体明确不写，是否同步系统字体，是否只限大字／小字；不得用“全字体”代替逐文件说明。
- **字形来源与构形**：SVG、扫描裁片、原生供体字形、部件轮廓、锚字、变换、单位和工具版本。部件组合必须记录轮廓索引和是否恒等变换。
- **实际操作**：命令、`--dry-run` 结果、备份路径、原子替换结果、机器流水路径和操作时间。
- **前后结果**：字体 SHA-256、字节数、cmap、glyphOrder、目标 glyph 名称、轮廓／点数／bbox、hmtx／vmtx，以及保留字形和度量比较结果。
- **验证证据**：chamfer 或其他闸值、源图／字体／浏览器渲染图、实际使用字体、测试与构建结果；明确哪些是回归辅助分数，不能把分数写成字符身份证明。
- **使用与限制**：正文或 `.gj` 是否更新、PUA 如何交换、系统字体缓存边界、尚未解决的视觉或数据问题。
- **回滚**：补前 Git blob 或按哈希备份、需要同时撤销的注册表／缓存戳／正文使用处，以及后续字体已变化时的单字移除方案。
- **提交**：字体提交和文档回填提交的完整哈希；若尚未提交，必须明确写“待提交”，提交后不得遗留该占位词。

详报可以汇总同一事件的多个字体，但必须逐文件列出结果，不能只记录一份字体的成功。

### 2.2 Changelog

在 `docs/font-changelog.md` 完成两处同步：

1. **当前正式补录状态表**：更新字位、当前版本、适用字体、Unicode／PUA 身份和详报链接。
2. **正式变更记录**：按时间倒序追加事件，说明“新增／替换／撤销／仅文档核验”，并记录来源、对象、前后哈希与字节数、cmap 变化、验证分数、缓存戳、提交和回滚入口。

Changelog 只记录已经发生或已经核实的事实。调研建议、未执行方案和临时试验必须放在相应章节，不能伪装成正式补录。

### 2.3 字体操作登记簿

在 `docs/font-operations.md` 追加一行并刷新当前哈希基线。每行至少有：

- 编号、Asia/Shanghai 时间、操作名称和目标码位；
- 目标字体文件及是否同步系统字体；
- 前后 SHA-256、字节数、cmap／glyphOrder 和保留字形结果；
- chamfer 或其他验证值、门槛、测试／浏览器结果；
- 缓存戳、Git 提交短哈希、详报链接和回滚点。

登记簿只保留当前基线和完整事件索引；旧基线写入事件或详报，不删除历史。

### 2.4 机器证据与源资产

根据操作类型归档到 `docs/research/evidence/<事件>/` 和 `tools/dataset/font-sources/`：

- `audit.json`：补录前身份、编码、字体覆盖和搜索范围；
- `patch-verification.json`：每次写入／替换的前后哈希、度量、保护检查、闸值和备份；
- `browser.json` 或等价记录：页面、字格、CSS 字体栈和平台实际字体；
- `annotation.json`：若同步正文或 `.gj`，记录替换前后哈希和计数；
- 冻结 recipe／SVG／扫描遮罩／锚字等可重建源；
- 脚本自动流水 `var/unencoded/kangxi-unencoded/font-patches.jsonl`（该目录通常被 gitignore，长期证据不可只依赖它）。

证据文件必须注明采集日期、输入路径和结果；不能把临时目录或不可复现的截图作为唯一证据。

### 2.5 注册表、应用说明与导航

- PUA：更新 `guji-preview-grid/src/pua-registry.json` 的 `version`、`source`、`font_versions`、`sha256_after`、`history`、适用范围和关联标准字符；新增或替换必须保存旧历史。
- 字体 URL 发生变化：更新 `guji-preview-grid/src/index.css` 的 `?v=` 缓存戳；注释中的版本也要同步。
- 应用覆盖或使用边界变化：更新 `guji-preview-grid/README.md` 的字体表和回退说明。
- 入口变化：更新 `README.md`、`docs/README.md`、`docs/research/evidence/README.md`，保证从导航能找到详报、Changelog、登记簿和规范。
- 正文或标注变化：只修改明确授权的页和字符，记录 `.gj`／JSON 前后哈希；不要把整批未审校草稿随字体提交。

## 3. 补录前检查清单

在选择写入工具前，逐项回答并保留结果：

1. 目标字符的身份是什么？页码、字头序号和原文是否能回到原图。
2. Unicode 是否已收录？已有码位是抽象字符还是精确字形变体？是否有标准化变体机制。
3. 每个目标字体是否已有映射、未映射字形、GSUB／format-14 调用或后备字体覆盖。
4. 本次是标准码位、PUA、字形修订、字体替换还是仅文档核验。
5. 字形源是否可归档并可重建？部件来源、锚字、单位、方向、孔洞缠绕和度量是否明确。
6. 目标范围是什么：`guji-large.ttf`、`guji-plane0.ttf`、plane2／planeF、系统字体，还是其中一部分。
7. 是否已记录补前 SHA-256、字节数、cmap、glyphOrder、目标及相关供体字形哈希，并建立按哈希命名的备份。
8. 是否有明确的验证闸和失败处理？没有闸值时不得用“看起来差不多”替代。

## 4. 执行与验证顺序

### 4.1 先干跑，再写入

使用目标工具的默认安全模式或 `--dry-run`，确认：

- 输入源、码位、目标字体和操作版本没有串错；
- chamfer／像素／结构验证通过；
- 除目标字形外，既有字形、hmtx、vmtx、cmap 和 glyphOrder 保持预期；
- 备份目录可写，机器流水能追加；
- PUA 的冻结配方能够重建出相同编译 glyf。

干跑结果应保存到机器证据，而不是只复制终端的一行输出。

### 4.2 正式写入

正式脚本应完成备份、验证、原子替换和流水追加。人工操作不得直接覆盖整份旧字体来“回滚一个字”，因为这会丢失后续补录。写入后立即重新计算文件哈希，并把实际结果写入详报、登记簿和注册表。

### 4.3 四层验收

| 层级 | 必查内容 | 通过条件 |
| --- | --- | --- |
| 字体结构 | cmap、glyphOrder、glyf、hmtx、vmtx、字体大小 | 目标变化符合预期，其余文件／字形保护检查通过 |
| 字形质量 | 源图或供体结构、bbox、轮廓方向、孔洞、闸值 | 不超过方案门槛；结构来源审查通过 |
| 应用渲染 | 大小字号、横竖排、目标页面、平台实际字体 | 页面显示目标字形，未落到系统回退 |
| 工程回归 | 生成器、JSON、测试、构建、`git diff --check` | 相关检查通过；失败项有明确归因和记录 |

## 5. 文档同步矩阵

| 变化 | 必须更新 | 通常不应修改 |
| --- | --- | --- |
| 新增标准码位 | 详报、Changelog、登记簿、证据、导航、目标字体说明、缓存戳 | PUA 注册表、无关正文、其他平面 |
| 新增 PUA | 上述全部 + PUA 注册表 + 冻结 recipe + 关联标准字符说明 + 使用处 | 标准 Unicode cmap、系统字体（除非明确授权） |
| 已有码位字形替换 | 详报、Changelog 历史、登记簿、前后字形证据、回滚备份 | 把替换写成“新增字符” |
| 字体文件／版本替换 | 登记簿哈希基线、Changelog、应用说明、缓存戳、回归证据 | 只更新文件名而不记录旧哈希 |
| 仅缓存戳更新 | 登记簿、Changelog（若影响发布行为）、应用说明 | 虚构字形变化或重复补录事件 |
| 仅调研未写入 | 调研报告、证据索引（标“未补录”） | 字体文件、正式补录表、PUA 注册表 |
| 撤销／回滚 | 详报撤销段、Changelog 逆向事件、登记簿、注册表／缓存戳／正文使用处 | 用旧整字体覆盖而不保护后续事件 |

## 6. Git 提交规范

1. 字体二进制、源 recipe、机器证据和对应报告应在同一个可审计变更集合中；字体文件一旦写入仓库，必须有 Git 提交作为回滚点。
2. 文档回填提交哈希可以单独提交，但回填完成后不能继续保留“待提交”“pending”等占位文字。
3. 工作区有并行任务时，使用明确路径和交互式暂存；提交前检查 `git diff --cached --name-status` 与 `git diff --cached`，不得用 `git add -A` 把校对草稿、实验产物或无关代码带入。
4. 提交前至少执行：冻结配方重建、JSON 校验、字体保护检查、目标页面或渲染图核对、相关测试、构建和 `git diff --check`。
5. 提交后把完整 commit 写回详报、Changelog、登记簿和机器证据；再检查 `git status`，确认暂存区为空或只剩明确属于其他任务的内容。

推荐提交顺序：

```text
<font-change>  字体、配方、证据、注册表、缓存戳和初版文档
<docs-followup>  回填字体提交号、最终哈希和登记簿链接
```

## 7. 回滚规范

- 先按事件查补前 SHA-256、Git blob 和按哈希备份，再决定恢复范围。
- 目标字体没有后续变化时，可以恢复对应补前文件；有后续补录时，必须制作针对目标字位的移除／替换并重新跑保护检查。
- PUA 回滚必须同步注册表版本／历史、共享字体哈希、缓存戳和正文使用处；标准码位回滚也必须同步 Changelog、登记簿和应用说明。
- 系统字体仅在原操作明确包含系统字体时回滚，并记录备份恢复和应用重启；仓库字体与系统字体不可互相覆盖。
- 回滚本身是正式字体操作，必须新增一条逆向 Changelog、登记簿和机器流水事件，不能删除原事件。

## 9. 完成定义

只有以下条件全部满足，才能把补录称为“已完成”：

- 字体文件已按目标范围写入并通过结构、字形、渲染和工程验证；
- 详报、Changelog、操作登记簿、机器证据和回滚点齐全；
- PUA 注册表、冻结配方、缓存戳、应用说明、导航和授权的正文使用处已同步；
- 文档中的哈希、版本、提交号和时间一致，没有 `pending`／“待提交”占位；
- 提交范围经过审查，未混入无关修改；
- 任何未通过的测试或浏览器限制都已在报告中明确说明，而不是宣称“全部通过”。
