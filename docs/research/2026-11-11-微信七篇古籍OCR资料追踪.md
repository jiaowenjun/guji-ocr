## 2. 古籍云 OCR：界面与工作流很贴题，开放程度需分开看

文章介绍的 V1.0 是针对古籍的桌面工作台，包含批量图像／PDF 导入、页面预处理、版面切分、人工画栏、正文和夹注排序、图文联动校对、工程保存、TXT 与可搜索 PDF 导出。

最值得借鉴的设计：

- **手工修正优先。** 正文列、注文、眉批、版心可以分别画框；注文可切换右先、左先或整框单行；同版式书可将人工版面应用到其他页。
- **多种切分后端。** 文章列出投影几何、行线感知、族谱、投影加 YOLO、纯 YOLO 等模式。族谱还需区分谱系图与族人记载页，不能把普通竖排排序规则直接套入。
- **图文逐列对校。** 点击文字定位图像，点击字格回到文字；分列校对和“写回校改”比只有一个大文本框更实用。
- **识别与版式可替换。** 帮助列出 RapidOCR／PP-OCRv6、Tesseract `chi_tra_vert`、PaddleOCR、CathayOCR ncnn Vulkan，以及“仅切分”模式。这是软件说明中的后端列表，本次没有逐一验证安装包内的实际模型和版本。
- **版式学习不应混称文字模型训练。** 文中“样式入库”用于自动检注、版式路由；不能据此认定已开放完整汉字识别模型的训练管线。

需要修正标题带来的几种印象：

| 宣传／表述 | 核查后的准确理解 |
| --- | --- |
| “首款”“全网首款” | 未见足够证据支持排他性历史判断，不作为本调研结论 |
| 免费、纯本地 | 作者声明默认离线；帮助同时有默认关闭的“AI 辅助转写（联网）”和在线出处检索。不能理解为所有功能永不联网 |
| 可自行训练 | 可以标注夹注并建立样式；标注器需另行联系作者取得，公开训练代码未确认 |
| 开源软件 | 本次未发现对应源码仓库和开放源代码许可证，归为“免费发布的桌面软件线索” |
| 识别率约 95% | 官网限定清晰刻本黑白图片；没有公开测试集、计分公式或独立验证 |

[官网资源页](http://gujiyun.cn/ziyuan.html)已提供[百度网盘下载入口](https://pan.baidu.com/s/13LDC3VUWyMITazO1qPErsA?pwd=ehha)，并注明“目前支持 win 系统”；同页分享说明禁止商业用途，仅允许个人日常研究和分享。**不应将它当成可直接商业集成的开源引擎。** 对本项目的价值主要是校对界面、手工干预、批量处理与版式模式设计。

文章列出的去红印、去版框／版心、二值化等功能，应保留可撤销原图：朱笔批校、鱼尾和版心可能正是研究对象。预处理是否改善识别必须用原图对照，不能只按“清理得更干净”判断。

## 3. dots.ocr／dots.mocr：结构化输出与两组看似矛盾的测试

### 3.1 原始论文与代码

| 资源 | 核实内容 | 对古籍的用处与边界 |
| --- | --- | --- |
| [dots.ocr 论文](https://arxiv.org/abs/2512.02498)，2025 | 统一学习版式定位、文字识别和阅读关系；发布 XDocParse 多语言评测 | 借鉴“位置＋类别＋文本＋顺序”输出；多语言成绩不代表古籍夹注能力 |
| [dots.ocr 仓库](https://github.com/studio-dots-ai/dots.ocr)／[权重](https://huggingface.co/rednote-hilab/dots.ocr) | 旧 `rednote-hilab` 仓库访问会转至 `studio-dots-ai`；当前 README 混有新 mocr 说明 | 必须固定模型名、权重 revision、代码版本；不能将当前 README 中的新模型命令直接当作旧版复现 |
| [Multimodal OCR: Parse Anything from Documents](https://arxiv.org/abs/2603.13032)，2026 | dots.mocr，3B；除文本外将图表、图示等转成结构化表示／SVG | 对含图表的古籍有探索价值，但 SVG 重绘不能取代原始文物图像保存 |

旧版“基于 1.7B LLM”描述的是语言骨干；当前对比表将整体模型列为约 3B。调研时需说明统计对象，不能把两个数字简单判成矛盾。dots.ocr-1.5 于 2026-03-19 改名 dots.mocr，这是官方更新记录中的关系。

两个仓库均有 MIT `LICENSE`，同时另附模型 `LICENSE AGREEMENT`。补充协议写明冲突时 MIT 优先，并包含商业使用、使用条件等条款。因此资源索引记录为“MIT＋附加模型协议”，而非只抄 GitHub 的许可徽标。本次未确认完整训练数据引擎、全套训练数据及从头训练复现材料。

### 3.2 11 页微信测试实际说明了什么

微信文章声称在 2026-07-22 使用 dots.mocr 官方在线演示逐页转写，以 Tesseract 5.5.2、`chi_tra_vert`、PSM 5 为对照。样本为 11 张约 1024×930 的扫描图，以序文和人物传记为主；去除空白、标点和缺字占位后，参考汉字共 1,829 个，繁简／异体字不合并。

| 文章报告的指标 | dots.mocr | Tesseract |
| --- | ---: | ---: |
| CER | 8.9% | 64.8% |
| 严格字符一致率 `1−CER` | 91.1% | 35.2% |

这是一组小样本参考转录一致性实验，不能得出 dots.mocr 已解决所有古籍，或 Tesseract 在各种合理预处理／切行配置下都会如此差的结论。文章自己也指出参考文本有疑似误录、繁简混杂和缺字。

它最有用的案例是**印章纳不纳入识别范围**：文中说模型读出了藏书印，而参考文本只含正文，于是被算成插入。正确的做法是预先定义正文、印章、版心、批注的评价范围，分区保存；不能事后因模型多读了字就任意改评分规则。

### 3.3 本次对样本仓库的代码核查

[AncientDoc_OCR](https://github.com/ziqian2001/AncientDoc_OCR) 是第三方教学／实验仓库，包含 11 张图、`gt.txt`、Tesseract notebook，不是 AncientDoc 官方维护的独立金标版本。本次读取其标签和 notebook，未运行 notebook：

1. `gt.txt` 有 11 条非空文本；统计所有 Unicode CJK Unified Ideograph 字符得到 **1,829**，与微信文章一致。它包含扩展区字 `㷔`、`䃅`、`䑓`。
2. notebook 的 `clean_chinese` 仅保留 `U+4E00–U+9FA5`，会丢掉上述三个字；且批量代码对预测清洗、对参考直接使用，存在评测口径不对称风险。古籍不能使用这个窄范围作为汉字全集。
3. notebook 先按**图片文件字节大小**排序，再用文件在该排序中的位置索引 `gt_lines`。这种隐式配对非常脆弱，应改成显式 `image_path → reference` 映射并人工核对；本次没有据此声称微信作者一定使用了错误配对。
4. 仓库没有此次 dots.mocr 演示测试的逐页输出、完整请求配置与评分脚本，不能独立复现 8.9%。在线演示的权重版本也未冻结。

核查计数与源文件哈希见[本轮证据记录](evidence/2026-11-11-wechat-source-checks.json)。这 11 页来源于 AncientDoc 系列材料，不应再当作与 AncientDoc 相互独立的测试库。

### 3.4 为什么与古籍酷的 69.24% 不一致

| 比较条件 | 微信 11 页测试 | 古籍酷 2026-04-03 博文 |
| --- | --- | --- |
| 总体结果 | dots.mocr 91.1% 严格一致率 | dots.mocr 69.24%“准确率” |
| 样本 | 11 页、1,829 字，以序文／传记为主 | 样本总数未公开；分夹注少、夹注多、写本 |
| 模型运行 | 7 月官方在线演示；未固定权重 | 4 月自部署测试；具体配置披露不完整 |
| 指标 | 明确 CER 与不合并异体字 | 准确率定义不足以核实等同 `1−CER` |
| 阅读顺序现象 | 作者称整体较好 | 作者报告经常误按从左到右排列 |

两者没有相同测试集、相同指标、相同模型快照和输出协议；因此不能相互否定。后续实验应保留两条假设：dots.mocr 可能在规整正文表现较好，但复杂夹注和方向排序可能仍是薄弱环节。用共同人工金标、固定模型和提示词才能检验。

## 4. HunyuanOCR-1.5：更适合研究微调与部署，但数据回流受许可约束

[论文](https://arxiv.org/abs/2607.04884)介绍约 1B 的端到端 OCR VLM；本次核对到 HTML v3。它延续 1.0 架构，主要升级数据构造、训练和推理速度：

- **DFlash 推测解码。** 草稿模型并行提出 token，目标模型验证。作者报告 Transformers 6.37×、vLLM 2.14×加速；OmniDocBench 单请求场景平均 3.032 秒／页降至 1.408 秒／页。这是该实验条件的成绩，不能换算成普通笔记本古籍处理速度。
- **Agentic Data Flow。** 根据模型错误提出数据需求，再搜集、验证、清洗和构造训练数据；值得借鉴错误分类与人校回流机制，但不是公开了全部生产训练数据。
- **训练开放程度较高。** [当前仓库](https://github.com/Tencent-Hunyuan/HunyuanOCR)有 `train/train_hunyuan.py`、DFlash 训练脚本及 `train_verl`，提供数据 JSONL 格式和打包说明；7 月 24 日又发布统一推理环境及 RL 栈，晚于微信文章。
- **部署入口明确。** Transformers、vLLM、DFlash 以及 llama.cpp／GGUF 路线均有官方文档；当前统一 GPU 环境要求 CUDA 13，另有较轻的分配置路径。是否适合本机仍需实际部署验证。

作者报告 OmniDocBench v1.6 为 **94.74**；Chronicles-OCR 古文字组／成熟书体组文本解析为 **0.54／0.79**。后者是归一化编辑相似度，不是 54%／79% 的单字框识别准确率，也不能代表古籍夹注检测成绩。文章关于无字负样本的讨论也有意义：空白、图案、破损不能被模型强行“读”出文本。

**与本项目最相关的限制来自[官方 LICENSE](https://github.com/Tencent-Hunyuan/HunyuanOCR/blob/main/LICENSE)。** 它采用 Tencent Hunyuan Community License，不是 Apache／MIT；地域排除欧盟、英国、韩国，超过约定月活规模有额外商业条款。第 5(b) 条禁止用其模型或输出改进其他 AI 模型，腾讯混元及其衍生模型除外。因此不能默认用混元生成的伪标签去训练 PaddleOCR／CHAT；“开放训练代码”与“输出可任意跨模型回流”是不同授权事项。

建议将其列为**可微调 OCR VLM 和部署研究候选**。若要跨模型共享训练数据，优先使用人工独立标注及授权清楚的数据，分别记录模型输出的来源和适用条件。

## 5. OvisOCR2：数据构造值得读，当前还需留意 OvisOCR3

[OvisOCR2 技术报告](https://arxiv.org/abs/2607.13639)和[模型卡](https://huggingface.co/ATH-MaaS/OvisOCR2)确认：0.8B、基于 Qwen3.5-0.8B、Apache-2.0，输入页图、按阅读顺序输出 Markdown；表格为 HTML，公式为 LaTeX，图像区域通过坐标占位。

论文最有价值的部分是训练数据与蒸馏路径：真实文档先经 PaddleOCR-VL-1.5 或 MinerU2.5-Pro 解析，统一结构并过滤；合成数据从同一 HTML 源生成图像和答案；4B 分支强化学习后，通过 on-policy distillation 转移给 0.8B，再融合候选权重。应注意教师解析错误仍可能传递，不能把“图文同源合成”或“人工抽查”理解为所有真实标签均正确。

| 作者报告的评测 | 分数 | 古籍选型时的含义 |
| --- | ---: | --- |
| OmniDocBench v1.6 Overall | 96.58 | 1,651 个 PDF 页上的文本／公式／表格等综合指标，不是古籍字符准确率 |
| PureDocBench Clean | 81.55 | 干净图像 |
| PureDocBench Digital | 77.09 | 数字退化图像 |
| PureDocBench Real | 66.56 | 真实退化图像；比 Clean 低 14.99 分，退化鲁棒性仍需实测 |

文中的“第一”限于当时比较表。公开资料提供权重、配置和推理示例；本次未确认完整训练集、合成引擎、奖励实现和 4B 教师权重的对应发布。OvisOCR2 的标准输出也没有逐字位置、字符置信度和候选字，不能只凭 Markdown 结果完成逐字图文校勘。

**版本更新：** 本次访问 OvisOCR2 卡已提示较新 [OvisOCR3](https://huggingface.co/ATH-MaaS/OvisOCR3)，对应[论文 arXiv:2610.33066](https://arxiv.org/abs/2610.33066)。OvisOCR3 模型卡仍为 0.8B／Apache-2.0，增加结构化 JSON、版式 JSON、一般 OCR 框、信息抽取和跨页表格等任务。本次只核对模型卡，未阅读全文或实测；不能将 OvisOCR2 的“只输出 Markdown”限制直接外推新版，也不能将区域框自动等同逐字置信对齐。

对于 guji-ocr，可将 OvisOCR2 作为固定历史基线，将 OvisOCR3 放入当前候选；先测竖列顺序、夹注召回、缺损页和异体字保真，再决定是否进入生产链路。

## 6. Chronicles-OCR：七书体评测，指标和标注有明确边界

[论文](https://arxiv.org/abs/2605.11960)当前为 2026-09-28 修订的 v2，晚于微信 6 月文章。本次阅读方法与评测说明，并直接核对[标注 JSONL](https://huggingface.co/datasets/VirtualLUO/Chronicles-OCR/blob/main/data/Chronicles_OCR.jsonl)和[官方评分代码](https://github.com/VirtualLUOUCAS/Chronicles-OCR/tree/main/Opensource)。

### 6.1 数据与任务

覆盖甲骨、金文、篆、隶、楷、行、草七种书体，含甲骨、青铜器、碑拓、纸本书法等载体。前 3 类采用字级框与现代汉字映射，后 4 类主要采用段落转写。

| 任务 | 覆盖 | 标注／指标 |
| --- | --- | --- |
| Spotting：定位＋释读 | 甲骨、金文、篆 | **IoU ≥ 0.75 且字符匹配**才算正确；主分数为 F1／H-mean；不能只看框重叠 |
| Fine-grained Recognition | 甲骨、金文、篆 | 图上红框指定字符，预测现代汉字，Exact Match；已标 `[UNK]` 的字符不采样 |
| Text Parsing | 七类 | 按阅读顺序转写；归一化编辑相似度，详见下式 |
| Classification | 七类 | 七书体分类准确率 |

官方代码还提供 bbox-only Detection F1 作为诊断指标；它与主 Spotting 的字符匹配要求不同。成熟四书体没有逐字框，不能当作七书体统一单字检测训练集，更没有古籍正文／夹注／眉批的语义标签。

论文把以下分数称作 NED，README／代码又使用 `1−NED` 名称；为避免方向混乱，以实际公式为准：

```text
score = 1 − Levenshtein(prediction, reference)
              / max(len(prediction), len(reference))
```

它越高越好，区别于 `CER = edit_distance / len(reference)`。代码会先去除 `[UNK]`／若干方块占位，再做文本归一化。0.79 不能直接换算为 21% CER，除非明确满足相同清洗与长度条件。

这里的 2,799 是不同路径数，**尚未对全体图片内容去重**。标注文件检查不等于人工审校质量结论；重复项和空框记录需要在复现清单中明确处理，不能暗中删除后仍声称与官方协议完全一致。

还有两个实际接入细节：甲骨字框可为 `[x,y,w,h]`，金文／篆书框可为坐标字典；官方 `utils/bbox.py` 已做格式转换，不能把所有列表直接当作 `[x1,y1,x2,y2]`。README 示例期待 `data/images/…`，而本次 HF 根目录可见各书体目录，需要按实际下载结构核对相对路径。

代码有 API／本地 vLLM 推理、纯规则评分和报告汇总入口，无需 LLM 裁判。仓库 `LICENSE` 为 Apache-2.0，但 README 的数据使用声明是 **research purposes only**；不要仅凭代码许可证认定整套图像可自由商用。

本项目优先使用其**隶／楷／行／草解析子集、严格框匹配和失败模式分析**；甲骨／金文／篆书仍属于原调研的扩展范围。主版式研究继续优先 SCUT-CAB、MTHv2、M5HisDoc。

## 7. PaddleOCR 综述的论文阅读路径

这篇文章主要提供背景，不新增受控古籍成绩。若需要理解现有工具的演进，以下是其有用书目：

| 论文 | 阅读目的 |
| --- | --- |
| [PP-OCR](https://arxiv.org/abs/2009.09941)、[PP-OCRv2](https://arxiv.org/abs/2109.03144)、[PP-OCRv3](https://arxiv.org/abs/2206.03001) | 检测、识别、轻量化与训练方法的工程演进 |
| [PP-StructureV2](https://arxiv.org/abs/2210.05391) | 文档版式与结构恢复；通用类别需向古籍适配 |
| [PaddleOCR 3.0 Technical Report](https://arxiv.org/abs/2507.05595) | PP-OCRv5、PP-StructureV3、PP-ChatOCRv4 的职责区别 |
| [PP-OCRv5: A Specialized 5M-Parameter Model Rivaling Billion-Parameter Vision-Language Models on OCR Tasks](https://arxiv.org/abs/2603.24373) | 当前 arXiv 标题与微信写法不同；小型识别模型与 VLM 的比较思路，识别裁片成绩不能外推整页 |
| [PaddleOCR-VL](https://arxiv.org/abs/2510.14528) | 文档视觉语言模型路线；需和当前 1.5／1.6 版本分开 |

这些书目已逐一核对 arXiv 标题与摘要，本次未将七篇全部通读。模型当前状态已在总调研核过，实际实验仍须固定版本、保留原始图像和字符规范。

## 8. 对 guji-ocr 的资源优先级调整

| 当前目标 | 新增优先项 | 与原有资源如何配合 |
| --- | --- | --- |
| 构建可校对的桌面／网页工作流 | 古籍云的手工画栏、分列校对、夹注顺序、工程保存设计 | 借鉴交互；实际引擎仍可用 CHAT／kraken、PaddleOCR 等 |
| 对照整页结构化解析 | dots.ocr、dots.mocr；当前 OvisOCR3 | 与 PaddleOCR-VL 同页比较，记录区域、阅读顺序和字符忠实度 |
| 研究自有古籍数据微调 | HunyuanOCR-1.5 的训练入口 | 先明确数据与输出许可；不默认允许跨模型伪标签训练 |
| 增加字形泛化测试 | Chronicles-OCR 的成熟书体子集 | 补充 EvaHan／自有抄本测试，不替代 SCUT-CAB 语义版式 |
| 快速检查评测脚本 | AncientDoc_OCR 的 11 页 | 只作教学小样本；先修正图文配对、Unicode 清洗、参考文本与区域范围 |

新增资源不会改变首轮应有的重点：用目标书籍建立独立人工金标，分别记录正文、夹注、眉批、版心、印章；按书／版本留出测试；分别评价字、行、区域、顺序与人工校对成本。通用榜单的 Overall、编辑相似度、CER、成功页准确率必须分栏记录，不能拼成一个排名。
