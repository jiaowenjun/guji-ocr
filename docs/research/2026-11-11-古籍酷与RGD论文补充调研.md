# 古籍酷博客与 RGD 论文补充调研

核查日期：2026-11-11。入口为用户指定的[古籍酷博客](https://ocr.gj.cool/blog)和 [IEEE 论文 8364534](https://ieeexplore.ieee.org/document/8364534/)。本次阅读了 8 篇相关博文、当前 API 文档、IEEE 论文全文，并核对论文表格与 AncientDoc 的实际发布文件。没有运行 OCR 模型或调用收费服务。

最有用的发现是：古籍酷提供了比较具体的古籍区域、大小字和校对接口设计；RGD 解释了如何利用识别结果获得紧致单字框；AncientDoc 的两个已知问题样例在当前发布文件中仍有可见错误或遗漏，应先审校再作金标。厂商自测、论文实验和本次文件核查的证据强度不同，以下分别说明。

## 2. 排版 2.0 与 API：最值得借鉴的设计

文章说明和[当前 API 文档](https://ocr.gj.cool/doc/v1)共同支持以下接口含义：

| 字段／参数 | 含义 | 对 guji-ocr 的启发 |
| --- | --- | --- |
| `layout_type=2` | 排版 2.0，启用自动区域检测，`area_ids` 有效 | 先分区域，再在区域内排文字列，减少跨区串行 |
| `layout_type=1`（默认） | 排版 2.0，沿用手工 `area`，不启用自动区域检测 | 明确“采用新版引擎”和“开启自动区域”是两个配置 |
| `layout_type=0` | 旧排版引擎，使用手工区域 | 做新旧排序对照时固定版本 |
| `AreaBBox`、`LineBBox`、`coors` | 区域、行、单字位置；单字框为 `[x1,y1,x2,y2]` | 保留位置，支持图文定位和逐字复核 |
| `chars`、`char_ids`、`line_ids`、`area_ids` | 字符与层级归属 | 不只保存一个扁平字符串 |
| `char_probs`、`coor_probs`、`option` | 识别置信度、定位置信度、候选字符 | 将漏检风险和认错风险分开呈现 |
| `anno` | 单字大小属性评分，接近 0 为大字，接近 1 为小字 | 大小字是视觉属性，不能直接等同正文／注释语义 |
| `layer` | 列号、列内子区域以及可能的夹注左右关系 | 为双行夹注保存局部关系，而非只按全页横坐标排序 |
| `text` | 按列换行，夹注可能以 `【】` 包围 | 便于阅读，但括号约定不能替代结构化关系 |

**“小字 ≠ 夹注”是这篇文章最实用的判断。** 页码、眉批、单列小字也可能很小；将一个小字概率当作夹注类别会混淆物理属性与语义。建议独立保存 `size_score`、`region_type`、`parent_region_id` 和阅读顺序。

倾斜校正会影响文字列归属和排序，应保留原图与变换关系。文章没有公开校正算法、角度范围或定量测试，因此不能据此认定已覆盖严重弯曲和任意局部变形。

当前文档还有需要集成时验证的边界：古籍接口明确写不支持数字、标点、字母；`area` 按传入顺序处理，但一处提示写“从左至右”，与常见古籍栏间自右向左不一致，不能照抄为通用规则。应以真实响应验证传入顺序与坐标约定。文章介绍的 `ocr_plus` 强调异体字保真，属于企业测试申请范围，不能假定普通 API 已默认开放。

春季技术报告中的 CNN + ViT 是**条件级联**：先用 CNN，难样本再交 ViT；并非已公开的融合编码器。作者报告 RTX 5060 Ti、平均约 347 字／页时达 0.14 秒／页，准确率最高 99.40%；更快模式为 99.26%。这些缺少公开测试集和全套配置，不能作为吞吐承诺，也不能与下面的生成式模型耗时直接横比。文中的“语义纠错”应在系统内单列，保留纠错前原始识别，防止语言模型把底本文字改成更常见写法。

标点文章的 `keep_wrap=1` 可保留换行；`target` 根据行内是否包含指定字符决定跳过哪些行。这是字符规则，不是可靠的标题／夹注语义分类器。

文章最值得转化为实验的问题有三个：

1. **夹注要单列评测。** 多个模型在“夹注多”上明显下降，不能用横排准确率选古籍系统。作者提到 dots.mocr 有将竖列从左向右排列的现象；这说明全页文本分数可能主要受顺序影响，而非单字识别本身。
2. **失败页必须计入。** 文中 Qwen 思考模式的高横排分数剔除了失败／重复输出；竖排 4B 思考模式在超时 300 秒、上下文 16,384 的设置下有 38% 失败，未给有效竖排分数。不能拿“成功页准确率”与其他模型的全量结果直接比较。
3. **记录实际输入输出链路。** PaddleOCR-VL-1.5 分数来自直接通过 OpenAI 兼容接口取文本，并未测完整检测／版式流水线。文章同组竖排平均耗时为 2.7 秒（Paddle）、14.1 秒（dots.ocr）、15.8 秒（chandra-ocr-2）、13.5 秒（Qwen 4B 关闭思考）；硬件和配置披露不足，适合作为复现线索。

缺失项包括可下载测试集、明确样本数与分层权重、完整金标规则、准确率公式、全部提示词和推理配置、完整逐页输出。该文支持把 PaddleOCR-VL-1.5 放入候选对照，**不能证明它对所有古籍最优，也不能把其分数转移到 1.6 或后续版本**。

### 4.3 对博客论证的修正

- **33.99% 是两份文本之间的差异，不能等同于数据集真实错误率。** 古籍酷也可能识别错、漏字或采用不同阅读顺序；需要独立人工审校的第三方参考。
- 博客把 58.83% 与 33.99% 相加推算总编辑量约 93%，依据不足：两次比较的参考、输出和编辑路径不同，不能相加成为可证的人工修订量。
- CER 大于 100% 在插入很多时数学上允许，本身不是数据造假的证据。
- 博客比较的是当时预印本与自测；原调研引用的是正式论文的其他模型／设置，不能把两组数值混成同一次实验。

**选用建议：** AncientDoc 可保留为困难样本与整页 OCR 研究资源；使用前固定文件哈希、去除重复路径、核实图文配对，并按书籍及版式分层抽样审校。正式报告 CER 时说明哪些标签已修订，保留原标签、修订标签和修订理由。当前不宜未经审校将其作为唯一裁决金标。

## 5. IEEE 论文：RGD 的方法、成绩与边界

**Hailin Yang, Lianwen Jin, Weiguo Huang, Zhaoyang Yang, Songxuan Lai, Jifeng Sun.** “Dense and Tight Detection of Chinese Characters in Historical Documents: Datasets and a Recognition Guided Detector.” *IEEE Access*, 6:30174–30183, 2018. [DOI:10.1109/ACCESS.2018.2840218](https://doi.org/10.1109/ACCESS.2018.2840218)。[作者数据仓库](https://github.com/HCIILAB/TKH_MTH_Datasets_Release)。

### 5.1 解决什么问题

密集汉字相邻很近，通用检测框即使 IoU 达到 0.5，也可能截掉笔画或混入邻字。论文因此关注 **tight character detection：紧致单字框定位**，在 IoU 0.7／0.8 等较严格阈值下评价。

流程为：整页垂直投影切竖行 → RGPN 识别引导候选网络（CNN、全连接、CTC）→ 利用非 blank 识别位置提出单字候选 → 回归网络输出更精确的字符框。

两个网络共享部分卷积特征，实验中共享前三层效果最好；定位损失只作用于有效候选。候选重复抑制结合重叠程度与识别字符：重叠且识为同字时，保留识别置信度更高者。这里的“context”是识别网络特征／标签信息，**不是在文本输出后用大语言模型润色纠错**。

论文将二值化行输入统一为 1000×100；实验 RGPN 输出类别维度为 1,472（包含 blank），与 TKH 的 1,471 字类对应，不能理解成覆盖完整汉字字符集。识别器先预训练 20 个 epoch，再训练检测。可借鉴的是识别与定位的联合约束，不必把这套 2018 年架构原样作为当前工程首选。

### 5.3 定量结果应怎样读

下表均为检测 **F-score（%）**，不是 OCR 字符准确率。数据来自[表 4](https://raw.githubusercontent.com/HCIILAB/SCUT_TKH_MTH_Datasets_Release/master/images/Results_of_Detection_Networks_on_TKH.png)和[表 5](https://raw.githubusercontent.com/HCIILAB/SCUT_TKH_MTH_Datasets_Release/master/images/Test_Results_on_MTH.png)。

| 方法 | 参数量 | TKH IoU 0.7 | TKH IoU 0.8 | MTH IoU 0.7 | MTH IoU 0.8 |
| --- | ---: | ---: | ---: | ---: | ---: |
| RGD | 9.29M | 94.60 | 83.82 | 88.17 | 61.54 |
| RGD-VGG16 | 64.02M | 94.98 | 85.85 | 91.29 | 73.01 |
| DMP-Nets-Line | 178.56M | 96.22 | 81.06 | 84.89 | 45.92 |
| TextBoxes-Line | 90.64M | 95.91 | 86.97 | 81.11 | 62.36 |

RGD 的优势是小模型和跨版本严格框定位表现；**不是每个条件下都第一**。例如 TKH 的 IoU 0.7 上 DMP-Nets-Line 更高，IoU 0.8 上 TextBoxes-Line 更高；MTH 的高阈值下 RGD-VGG16 更强。表 4 上半部的其他基线用整页输入，下半部 `-Line` 用行输入，应优先看输入条件相同的比较。

摘要的 **97.25%** 是引导识别网络的识别成绩，不是整页 OCR 正确率或版式准确率。预训练段落另报 AR 95.44%、CR 97.34%，也不应混作检测分数。

### 5.4 对古籍竖排任务的限制

1. **切行是前置条件。** 论文明确说明，MTH 实验为简化实现，保证每个切分输入只有一行字。它没有证明能自动处理任意复杂整页、双行夹注和区域顺序。
2. **检测召回受识别器限制。** 只有识别器提出的字符才有定位候选，识别漏掉的字可能直接无框；要单独观察罕见字和低质图像的漏检。
3. **没有古籍语义版式输出。** 单字框不会自动给出正文／眉批／版心分类，也不会建立注释与正文的父子关系。
4. **数据公开不等于代码公开。** 当前关联仓库可见数据说明、图片和网盘入口，本次未发现完整 RGD 训练实现及权重；不要将其列成已验证可运行的开源 OCR 系统。

## 6. 对原调研与后续实验的调整

| 调整 | 理由与具体做法 |
| --- | --- |
| AncientDoc 从“直接用作补充基准”改为“先审校的研究资源” | 本次确认实际文件数量差异和样例遗漏；完整记录版本、样本清单和修订金标 |
| 版式输出采用区域—行—字三级结构 | 借鉴古籍酷接口，但将大小字属性、语义类别、注释依附与阅读顺序分开 |
