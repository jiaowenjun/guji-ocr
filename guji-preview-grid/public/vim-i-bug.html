vim I 键代理对缺陷演示

@replit/codemirror-vim 6.4.0 · 引擎源码 vim.js 的 updateSelectionForSurrogateCharacters 误伤 I（firstNonBlank 路径）——与 guji-preview-grid 的集成无关，是上游缺陷。

先点编辑器获得焦点（或点下方按钮定位光标），再按演示步骤操作。每行演示一个变量。

复现步骤

  1. 第 1 行 #𠃕（𠃕 = U+200D5，UTF-16 代理对）：光标放到 𠃕 上，按 I —— 缺陷：进入 insert 但光标落在 # 之后（ch=1），不在行首。
  2. 对照组 A：同一位置先 A 再 Esc 再 I —— 正常：光标到行首。差异原因见下方分析。
  3. 对照组 B：第 2 行 #一（BMP 汉字，单码元）同样按 I —— 正常。触发条件是「光标停在高代理位」，不是汉字本身。
  4. 对照组 C：第 4 行 古𠃕，光标放 𠃕 上按 I —— 同样缺陷：落在 古 之后（与 # 无关，任何「光标在高代理位 + 同行跳到行首」都触发）。

根因链

function updateSelectionForSurrogateCharacters(cm, curStart, curEnd) {
  // 守卫本意是「移动了一格」（normal 光标在字上、选区边界差 1 的半开偏移），
  // 但 curStart.ch >= curEnd.ch - 1 对一切同行后退移动恒真——包括跳到行首：
  if (curStart.line === curEnd.line && curStart.ch >= curEnd.ch - 1) {
    var charCode = cm.getLine(curStart.line).charCodeAt(curStart.ch);
    if (0xD800 <= charCode && charCode <= 0xD8FF) {  // 上界应为 0xDBFF（笔误）
      curEnd.ch += 1;   // ← 把正确的行首 {0,0} 掰成 {0,1}，光标即落在 # 之后
    }
  }
  return {start: curStart, end: curEnd};
}
  • 触发三条件：旧光标停在高代理码元上（本例 0xD840，𠃕 的高半区）＋ 同行后退移动 （I 跳行首必满足）＋ 高代理值恰在 0xD800–0xD8FF（0xD900–0xDBFF 因上界笔误反而躲过，即 U+40000 以上的字不触发）。
  • 为何 A→Esc→I 正常：A 进 insert 于行尾（eol 分支不经过修正器）； Esc 退回 normal 时光标按码元 −1 落在低代理位（ch=2，0xDCD5）， 不在修正器认定的「高代理」区间 → 修正器不动作 → I 得到正确的行首。
  • 影响面：仅 I（normal，firstNonBlank 路径）。a（charAfter）、 r、d/y/c 的选区边界走同一函数是设计内用法（跨代理对整字操作）， i / A / o / O 不经过该函数，均正常。

规避方案（本页可开关体验）

  • 映射 Vim.map("I", "^i", "normal")：^（motion）与 i （inplace）都不经过修正器，行为与 I 等价（首非空进入 insert）。已验证修复本缺陷且保留计数前缀。
  • 根治须上游修 updateSelectionForSurrogateCharacters：守卫收窄为「移动恰为一格」 （|curEnd.ch - curStart.ch| <= 2 且目标/起点跨代理边界），或 firstNonBlank 分支不再过修正器。
